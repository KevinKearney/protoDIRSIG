# protoDIRSIG SDK API: operations

Status: proposed. Contract version `sdk-api/1`.

The operation set of the SDK. The Python facade and the REST API expose the same operations with the same inputs, outputs and errors. `Mode` is `pure` (no state is created or changed; the same inputs give the same output), `sync` (changes state and completes before returning) or `async` (returns an id at once; the work continues, and its state is read with `get_run` or `get_sweep`). Every error is a problem details object (RFC 9457); an error caused by an authored file carries `layer` (the file, relative to the library root) and `field` (the field in that file). `Today` names the existing code the operation would be built on, or `none`. `Status` is `built`, `partial` or `gap`. Requirement ids refer to `requirements.md`.

Every operation has two forms with the same inputs, outputs and errors: a Python method of the SDK facade, with the operation's name, and a REST path in `openapi.yaml` (R-06). The rows below therefore do not cite R-06 one by one.

Identifiers. A run id is the sha256, as 64 lowercase hex digits, of the canonical JSON serialization (RFC 8785, the JSON Canonicalization Scheme) of the resolved run spec. The resolved run spec is the parsed `run-spec/1` document with its sensor block materialized: a sensor given by reference (`ref: {name, content_hash}`) is replaced by the `sensor` block of the referenced `sensor-spec/1` document, so the same spec with its sensor inline or by reference has the same run id. The serialization covers the document only. It excludes the comment header that names the recipe a spec was composed from, and the composition provenance (the layer file and hash of each member) that `compose` returns beside each spec; the `provenance` label of each value in `settings` is part of the document and is included. A sweep id is the sha256, as 64 lowercase hex digits, of the canonical JSON serialization of the sorted array of its run ids, so a sweep is identified by the runs it contains, not by the bytes of the recipe that produced them. Because both ids are derived by the backend from content, two different submissions cannot share an id. The SDK computes both (`protodirsig.identity`); `manifold_contracts/vectors/identity/` holds conformance vectors for the canonicalization and the ids.

## Run states

A run has one of five states. A run exists only once it has been admitted. Admission, the `none` level of `validate`, runs synchronously inside `submit_run` and `submit_sweep`; a submission that fails it is answered with a 422 problem response, and creates no run, no id and no stored record. Execution after admission is asynchronous.

| State | Meaning | Final |
|---|---|---|
| `accepted` | admitted: the run spec composes, is valid `run-spec/1`, its references resolve and match their content hashes, and its library files are present; waiting to execute | no |
| `running` | executing: the DIRSIG dry run of the assembled job, then the render | no |
| `rendered` | execution finished; the artifacts are available | yes |
| `failed` | execution stopped with an error, including a DIRSIG dry-run failure at the start of execution; `errors` gives it | yes |
| `cancelled` | cancelled before it finished | yes |

Transitions: `accepted` to `running`; `running` to `rendered` or `failed`; `accepted` or `running` to `cancelled`. A sweep has no state of its own: `get_sweep` reports the state of each of its runs, and a run that fails or is cancelled does not change the others. `LocalBackend` makes every state observable: each run's `status.json` in the run store holds it, the worker moves it by compare-and-set (so a cancelled run is never overwritten), and a run whose worker died is reported `failed` with an `execution` problem.

## Where the code departs from the contract today

- There is no REST form yet: `openapi.yaml` describes it, but the server and `RemoteBackend` are not built, so every operation exists only as a Python method (`Workspace`, over `LocalBackend`).
- `LocalRegistry` and `Simulation` keep the older shapes for the notebooks: a rejected submission is a state (`SubmissionResult.verdict`, `RunStatus.state` `rejected`), `LocalRegistry.submit_sweep` admits each run on its own, results are paths in memory, `run`/`run_sweep` block until DIRSIG finishes, and `LocalRegistry.submit` validates (with the dry run) and executes in one object. `LocalRegistry` is deprecated in favour of `Workspace`.
- `get_artifact` reads the whole file into memory; there is no streaming for large artifacts.
- `LocalBackend` runs on POSIX hosts only: the run store and the worker use `fcntl` locks and process groups.
- Re-executing an identical run spec, for example to check that a seeded render reproduces, is not part of `sdk-api/1`: resubmission returns the existing run. A later version may add it.
