# protoDIRSIG SDK API: requirements

Status: proposed. Contract version `sdk-api/1`.

These are the requirements the SDK API is written against. Each one is verified by an existing test, or marked `gap` where no test covers it yet. `Status` is `met` (built and tested), `partial` (part of it is built or tested, the rest is not) or `gap` (not built). The operations that serve each requirement are listed in `operations.md`.

| Id | Requirement | Rationale | Verified by | Status |
|---|---|---|---|---|
| R-01 | The SDK is usable on its own, without any MANIFOLD service: a user can compose, validate and execute runs on one machine with a DIRSIG installation. | The SDK is a tool for DIRSIG users first; submitting to MANIFOLD is a later, optional step. | `test_submit_and_run_sweep_keep_each_run_independent`, `test_real_spec_passes_all_three` | met |
| R-02 | Composing a recipe and validating a run spec work offline: no server, no network, and no change to any library file. | Authors iterate on YAML locally; a contract that needs a server to tell them their recipe is wrong is unusable offline. | `test_composition_is_deterministic`, `test_vector`, `test_real_spec_passes_all_three` | met |
| R-03 | Every run is reproducible from authored YAML: the run spec a run executes is composed from tracked layer files, and the tracked composed spec equals what the layers compose to. | A run that cannot be regenerated from its sources cannot be audited or repeated. | `test_generated_run_specs_are_current`, `test_composition_is_deterministic`, `test_sweep_composition_is_deterministic` | met |
| R-04 | A sensor is described once, in one library file, and run specs refer to it by name and content hash; it is never copied per run or per engine. | Copies drift; one file per sensor keeps every run that uses it consistent. Only one engine (DIRSIG) exists, so "per engine" is shown for that engine only. | `test_sweep_runs_one_spec_per_sensor`, `test_explain_names_the_layer_of_every_member`, `test_edited_sensor_spec_fails_resolution` | partial |
| R-05 | One recipe can fan out across several sensors, composing one run per sensor with the scenario, engine profile and seed shared. | Comparing sensors on the same scene is the common study, and it must not mean copying the scenario. | `test_sweep_runs_one_spec_per_sensor`, `test_vector` | met |
| R-06 | Every operation has a REST form, so the same operation set is available from Python and over HTTP. | A REST wrapper serves users who do not run Python locally; one operation set keeps the two in step. | gap | gap |
| R-07 | Run results are returned as artifact references `{name, sha256, media_type, uri}`, with `file://` URIs locally and download URLs remotely, never as bare paths. | A path is meaningful only on the machine that wrote it; a reference with a hash is portable and verifiable. | gap | gap |
| R-08 | Errors use one model, problem details (RFC 9457), and an error caused by an authored file names the layer file and the field in it. | Users fix YAML; an error must point at the line they wrote, not at the composed document or a stack trace. | `test_errors_name_the_layer_file_and_field`, `test_vector` | partial |
| R-09 | A run id is derived from the composed run spec's bytes, so submitting the same run twice returns the same run; a sweep id is derived from the recipe's bytes. | Content-addressed ids make resubmission idempotent and let a result be traced to the exact spec that produced it. | `test_sweep_id_is_the_recipe_hash_and_stays_out_of_the_specs` | partial |
| R-10 | A seeded run is byte-reproducible: the same run spec, rendered twice, gives identical images. | Reproducibility is checked by comparing bytes, which needs determinism, not statistics. | `test_run_sweep_renders_each_run_as_it_renders_alone` | met |
| R-11 | A documentation site is generated from this contract (schemas, OpenAPI document) and the SDK's docstrings. | One source for the reference documentation keeps it in step with the code. | gap | gap |
| R-12 | Library resources (sensors, scenarios, engine profiles, recipes) can be listed and read through the API. | A user, or a REST client with no file access, must be able to see what can be composed. | `test_load_sensor_spec` | partial |
| R-13 | Submission is asynchronous: it returns a run or sweep id at once; state is read by id; a run that has not finished can be cancelled. | Renders take seconds to many minutes; a caller must not block, and must be able to stop work it no longer needs. | gap | gap |
| R-14 | Within a sweep each run has its own state, and a rejected or failed run never stops the others. | One bad sensor file must not cost the rest of a sweep. (From the code: `LocalRegistry.run_sweep`.) | `test_submit_and_run_sweep_keep_each_run_independent` | met |
| R-15 | Every composed run spec is a valid `run-spec/1` document, so a run composed by the SDK is accepted wherever `run-spec/1` is. | The SDK's composition must not create a dialect. (From the code: the run-spec checks applied to every composed run.) | `test_every_composed_run_passes_the_run_spec_checks` | met |
| R-16 | Referenced files are verified against their stamped content hash when read, and a mismatch is an error. | A reference that silently resolves to edited content breaks reproducibility. (From the code: `run_spec` hash verification.) | `test_edited_sensor_spec_fails_resolution`, `test_stamped_hash_rejects_a_corrupt_asset_at_resolution` | met |
