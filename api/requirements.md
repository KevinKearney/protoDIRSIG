# protoDIRSIG SDK API: requirements

Status: proposed. Contract version `sdk-api/1`.

These are the requirements the SDK API is written against. Each one is verified by an existing test, or marked `gap` where no test covers it yet. `Status` is `met` (built and tested), `partial` (part of it is built or tested, the rest is not) or `gap` (not built). The operations that serve each requirement are listed in `operations.md`.

| Id | Requirement | Rationale | Verified by | Status |
|---|---|---|---|---|
| R-01 | The SDK is usable on its own, without any MANIFOLD service: a user can compose, validate and execute runs on one machine with a DIRSIG installation. | The SDK is a tool for DIRSIG users first; submitting to MANIFOLD is a later, optional step. | `test_submit_and_run_sweep_keep_each_run_independent`, `test_real_spec_passes_all_three` | met |
| R-02 | Composing a recipe and validating a run spec work offline: no server, no network, and no change to any library file. | Authors iterate on YAML locally; a contract that needs a server to tell them their recipe is wrong is unusable offline. | `test_composition_is_deterministic`, `test_vector`, `test_real_spec_passes_all_three`, `test_validate_none_needs_no_engine`, `test_engine_free_validation_runs_with_the_engine_packages_unimportable` | met |
| R-03 | Every run is reproducible from authored YAML: the run spec a run executes is composed from tracked layer files, and the tracked composed spec equals what the layers compose to. | A run that cannot be regenerated from its sources cannot be audited or repeated. | `test_generated_run_specs_are_current`, `test_composition_is_deterministic`, `test_sweep_composition_is_deterministic` | met |
| R-04 | A sensor is described once, in one library file, and run specs refer to it by name and content hash; it is never copied per run or per engine. | Copies drift; one file per sensor keeps every run that uses it consistent. Only one engine (DIRSIG) exists, so "per engine" is shown for that engine only. | `test_sweep_runs_one_spec_per_sensor`, `test_explain_names_the_layer_of_every_member`, `test_edited_sensor_spec_fails_resolution` | partial |
| R-05 | One recipe can fan out across several sensors, composing one run per sensor with the scenario, engine profile and seed shared. | Comparing sensors on the same scene is the common study, and it must not mean copying the scenario. | `test_sweep_runs_one_spec_per_sensor`, `test_vector` | met |
| R-06 | Every operation has a REST form, so the same operation set is available from Python and over HTTP. | A REST wrapper serves users who do not run Python locally; one operation set keeps the two in step. | gap | gap |
| R-07 | Run results are returned as artifact references `{name, sha256, media_type, uri}`, with `file://` URIs locally and download URLs remotely, never as bare paths. | A path is meaningful only on the machine that wrote it; a reference with a hash is portable and verifiable. | `test_submit_run_returns_at_once_and_renders`, `test_a_multi_frame_run_lists_per_frame_artifacts`, `test_artifact_references` | partial: `LocalBackend` returns `file://` references with `sha256`, `media_type` and `frame`; download URLs need the remote backend (phase 3), and `LocalRegistry` and `Simulation.run` still return paths for the notebooks |
| R-08 | Errors use one model, problem details (RFC 9457), and an error caused by an authored file names the layer file and the field in it. | Users fix YAML; an error must point at the line they wrote, not at the composed document or a stack trace. | `test_errors_name_the_layer_file_and_field`, `test_vector`, `test_locate_agrees_with_the_composers_provenance_for_every_member`, `test_a_mutated_layer_is_named_by_file_and_field`, `test_a_sensor_violation_is_named_in_the_sensor_library_file`, `test_submission_problem_names_the_engine_profile_field`, `test_admission_problem_example_names_the_edited_engine_profile_field`, `test_a_resolution_failure_names_the_layer_file_and_field`, `test_problem_errors_carry_conforming_problems`, `test_compose_error_is_a_problem_naming_layer_and_field`, `test_an_unstamped_reference_is_refused`, `test_a_sweep_with_a_failing_member_creates_nothing`, `test_unknown_ids_raise_not_found`, `test_a_killed_worker_leaves_a_failed_run`, `test_the_atmosphere_refusal_names_the_engine_profile_field`, `test_the_weather_refusal_names_the_engine_profile_field`, `test_the_platform_template_refusal_names_the_engine_profile_field` | met: through the Backend every error is a problem details object, raised as a `ProblemError` or recorded in a run's `errors` (composition, schema, resolution, unstamped, not found, execution), and one caused by an authored file names its layer file and field; below the Backend, the composer and the loader raise `ComposeError` and `RunSpecError`, which the Backend maps |
| R-09 | A run id is the sha256 of the canonical JSON serialization (RFC 8785) of the resolved run spec (its sensor block materialized; the header naming the recipe and the composition provenance excluded), so the same run submitted twice, with its sensor inline or by reference, is the same run; a sweep id is derived from its sorted run ids. | Content-addressed ids make resubmission idempotent and let a result be traced to the exact spec that produced it. | `tests/test_identity.py` (`test_invariances`, `test_compose_vector_run_ids`, `test_sweep_ids`), `test_sweep_id_is_derived_from_the_run_ids_and_stays_out_of_the_specs`, `test_submissions_carry_their_run_ids`, `test_resubmission_returns_the_existing_run` | met |
| R-10 | A seeded run is byte-reproducible: the same run spec, rendered twice, gives identical images. | Reproducibility is checked by comparing bytes, which needs determinism, not statistics. | `test_run_sweep_renders_each_run_as_it_renders_alone` | met |
| R-11 | Contract-level: the reference documentation site is generated from this contract (the operation table, the schemas and the OpenAPI document) and the SDK's docstrings, so every description in the contract is written for an external reader. | One source for the reference documentation keeps it in step with the code. | gap | gap |
| R-12 | Library resources (sensors, scenarios, engine profiles, recipes) can be listed and read through the API. | A user, or a REST client with no file access, must be able to see what can be composed. | `test_load_sensor_spec`, `test_every_file_is_listed_with_its_digest`, `test_get_round_trips_every_resource`, `test_the_library_lists_every_resource`, `test_the_library_reads_every_resource`, `test_the_library_family_returns_models_equal_to_the_backend_documents` | met |
| R-13 | Submission is admitted synchronously and executed asynchronously: a submission that passes admission returns its run or sweep id at once, and one that fails admission is answered with an error and creates no run; state is read by id; a run that has not finished can be cancelled. | Renders take seconds to many minutes; a caller must not block, and must be able to stop work it no longer needs. | `test_submit_run_returns_at_once_and_renders`, `test_an_unstamped_reference_is_refused`, `test_a_sweep_with_a_failing_member_creates_nothing`, `test_cancel_an_accepted_run_and_a_final_run`, `test_cancel_a_running_run_stops_its_processes`, `test_unknown_ids_raise_not_found`, `test_two_instances_see_the_same_runs` | met |
| R-14 | Within a sweep each run has its own state, and a run that fails or is cancelled never stops the others. | The renders of a sweep can take many minutes in all; one failed render must not cost the user the others, and the user must be able to see which run failed and why. | `test_submit_and_run_sweep_keep_each_run_independent`, `test_a_cancelled_sweep_run_does_not_change_the_other`, `test_a_killed_worker_leaves_a_failed_run` | met |
| R-15 | Every composed run spec is a valid `run-spec/1` document, so a run composed by the SDK is accepted wherever `run-spec/1` is. | A user who composes with the SDK must be able to hand the result to any tool that reads `run-spec/1`, without learning a second format. | `test_every_composed_run_passes_the_run_spec_checks`, `test_a_passthrough_recipe_composes`, `test_documents_valid_before_stay_valid` | met |
| R-16 | Referenced files are verified against their stamped content hash when read, and a mismatch is an error. | A user who repeats a study must get the inputs it was run with; a reference that silently resolved to edited content would give a different result under the same name. | `test_edited_sensor_spec_fails_resolution`, `test_stamped_hash_rejects_a_corrupt_asset_at_resolution`, `test_stale_scene_digest_fails_resolution` (a scene directory, by its `dirhash/1` digest), `test_submit_refuses_an_unstamped_reference`, `test_a_digest_mismatch_is_refused` (a pass-through directory, by its `dirhash/1` digest), `test_a_tampered_library_directory_fails_at_execution` | met |

Contract-level requirements (served by the contract as a whole, not by an operation): R-11. It is met by the form of this folder, an operation table, payload schemas and an OpenAPI document whose descriptions a documentation generator can render, together with the SDK's docstrings. R-06 also applies to every operation; `operations.md` cites it once, in its preamble, rather than on each row.
