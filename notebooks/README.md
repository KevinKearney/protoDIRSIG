# Notebooks

Several kinds of notebook live here, and they're not interchangeable.

**Stage notebooks** (`stage_NN_<slug>.ipynb`, top level) are the active, accumulating work: each one builds toward a MANIFOLD-conformant template notebook, one stage at a time. A later stage extends what an earlier one does rather than rewriting it, so the stage notebooks are expected to keep changing as work continues — this file describes their current state, updated as they go, not a history of how they got there. Stage 06 is the exception to building on a render: it reads recorded results (`docs/data/s2s_results.jsonl`) and renders nothing.

**`dirfm_tutorials/`** are standalone tutorials in `dirfm` usage: each is self-contained, driven directly through `dirfm` with no MANIFOLD run-spec or registry layer involved, and not part of the stage progression. They stay as worked examples.

**`dev/`** holds discovery-log notebooks — working notes from exploring a received tree or tool behavior before the pattern was understood well enough to write cleanly. Kept as executed, not maintained going forward.

**`sidebars/`** holds side investigations: exploratory like `dev/`, but tracked, because their results are cited in the CONOPS and Guide.

## Stage notebooks

- **`stage_01_auror_from_runspec.ipynb`** — Builds and renders the AUROR_ref DIRSIG job driven entirely from a MANIFOLD run-spec YAML (`manifold_run_specs/auror_ref.yaml`), via `packages/core/src/manifold/core/run_spec.py`. Scene, platform, atmosphere, weather and seed all come from the run spec rather than being written into the notebook's cells; the assets resolve in `manifold_config_repo/`, and the motion and tasks files are generated from the spec.
- **`stage_02_conformance_template.ipynb`** — Submits the same job through `LocalRegistry` (schema, resolution and execution checks) and renders it with `Simulation.run()` only if accepted, capturing DIRSIG's JSON run/info logs alongside the render. This is the current conformance-template notebook. As received, the vehicle target never appears, so the notebook adds an oversized (8-pixel) Lambertian disk that flies with it. The disk goes into a mirror of `manifold_config_repo/` under `outputs/`; `manifold_config_repo/` itself is unchanged.
- **`stage_03_sensor_sweep.ipynb`** — The same scenario through different sensors. Shows the sensor library (`manifold_sensors/`), one entry's blocks, the three spectral curves, and the channel response the generator writes into each `.platform`. Then composes the sweep recipe `manifold_run_specs/recipes/sensor_sweep_tahoe.yaml` into one run per library sensor (`compose_sweep`), submits every run (`LocalRegistry.submit_sweep`) and renders all three in 32 × 32 windows (`run_sweep`, seconds each). Compares the ground sample distance measured from the geolocation truth with pitch ÷ focal length × range. Closes with what is synthetic and what is not. Finds DIRSIG and `dirfm` through `external/` (`scripts/bootstrap.py install`), with no home-directory paths.
- **`stage_04_leo_pass.ipynb`** — A moving platform: the recipe `manifold_run_specs/recipes/leo_pass_tahoe.yaml`, a WORLDVIEW-2 pass over the Tahoe scene whose `engine.motion` has kind `orbit` (a library TLE propagated over a 120 s window into ECEF waypoints, LookAt at the scenario point). Composes and explains it, validates it without the engine and then with the DIRSIG dry run, renders three 16 × 16 frames 10 s apart around culmination, and checks them independently: the platform position recovered from each frame's truth against the track, the ground track against one from the `sgp4` package and GMST-1982, the frame-centre intercept against the target, and the frame spacing against the speed. Needs no network.
- **`stage_05_sdk_auror_demo.ipynb`** — The SDK end to end, through public surfaces only: the `Workspace` (library reads, compose, validate, submit, status and verdict, artifacts), the run-spec loader and the engine-block schema `list_engines` publishes. Builds a recipe document from the library's `auror_ref` (a 16 × 16 window, and a copy of its engine profile with `resources.cpu_threads: 1`, in a library copy under `outputs/stage_05_sdk_auror_demo/`), composes it and shows the run spec, its run id and provenance, writes it to a file and reads it back with the loader, checks the engine block against the published schema, validates it (engine-free and with the DIRSIG dry run) and shows one deliberate refusal (a uniform `BasicAtmosphere` with no weather values, refused with DIRSIG's reason), submits it, lists the artifacts by role with the verdict, renders the same recipe again in a second work root (same run id, byte-identical product), and compares the MaterialMap1 demo in the layered form with its pass-through run at 16 × 16 using the layered-comparison metric (`scripts/compare_layered.py`; the demo's values are derived at run time into the state directory, outside the repository, and not printed). Ends with the values a cell needed that the SDK does not expose. Runs in about 30 s; without DIRSIG the engine-free steps run and every other cell prints why it skips. Executed by `tests/test_stage05_notebook.py`.
- **`stage_06_space_to_space.ipynb`** — The space-to-space results against their closed forms, from the records alone: reads `docs/data/s2s_results.jsonl` (written by `scripts/s2s_measure.py`) and the `TOL_*` tolerances of `tests/test_s2s_results.py` (parsed, not imported), and reproduces every case that test asserts. Plots, each against its model: the 20 m plate's flux and footprint against range, exposure scaling, the Sun's zenith (plate and barred background), the 10 m sphere's Lambertian phase function (with the unresolved 0.25 m sphere beside it), and the 0.5 m plate, labelled and unlabelled, against the R⁻² line with its sub-pixel breakdown (no test tolerance; residuals printed alone). Each residual is printed beside the test's tolerance, with a summary table. Ends with a table of what the SDK cannot express for this geometry, from `docs/Space_to_space_characterization.md`. Renders nothing; no DIRSIG, network or GPU; runs in a few seconds. Executed by `tests/test_stage06_notebook.py` (under 60 s).

## `dirfm_tutorials/`

- **`tutorial_dirfm_basics.ipynb`** — `dirfm`'s own building blocks: materials, primitives, sensor trees, motion, atmosphere, GLIST mesh geometry, multi-scene composition, and determinism/render-quality knobs.
- **`tutorial_orbit_to_ground.ipynb`** — An orbit-to-ground SDA/orbital scenario, reconstructed directly with `dirfm`.
- **`tutorial_tacoma_scene.ipynb`** — A WorldView-2 pass over DIRSIG's Tacoma scene, driven directly through `dirfm`.
- **`tutorial_auror_scene.ipynb`** — The AUROR_ref job (same scene and platform the stage notebooks use), driven directly through `dirfm` with no run-spec or registry layer. A plain usage example, not part of the staged work. Reads AUROR_ref's files from their copies in `manifold_config_repo/` and `tests/fixtures/auror_ref/`, since `AUROR_ref/` itself was retired.

## `sidebars/`

Side investigations that a stage or tutorial raised but that don't belong in one: exploratory, kept as executed, and tracked (unlike `dev/`, which `.gitignore` keeps local). Each notebook keeps any assets it adds in a folder of the same name beside it.

- **`vehicle_point_source.ipynb`** — Distils the real AUROR vehicle mesh, given a reflective material, into a radiant intensity from a close-range DIRSIG render at the task's exact sun and view angles. Writes it as a `.int` point source, and renders the 500 km scene with it. Also renders the received 1500 K emitter with thermal prediction forced. Results are summarised in the CONOPS and Guide, section 9.
