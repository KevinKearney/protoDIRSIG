# Authoring the layered DIRSIG form

This guide is for a DIRSIG5 user who writes `.sim`, `.platform` and `.scene` files and wants the same job stated as a `run-spec/1` document. It describes what the SDK does at this commit; the contract itself is section 3 of the [CONOPS and Guide](MANIFOLD_DIRSIG_CONOPS_and_Guide.md), and the engine block's schema is `manifold_contracts/dirsig-engine-1.schema.json`. Every code block below is a spec excerpt or a command the repository already runs; `tests/test_authoring_guide.py` parses each block, compares each spec excerpt with the file it names and admits that file.

## Two forms of one DIRSIG job

A DIRSIG run spec has the keys `spec_version`, `descriptor` and `engine`. The engine block (`dirsig-engine/1`) takes one of two forms.

- **Layered.** The engine block states the scene, the platform, the motion, the task windows and the atmosphere; `descriptor.sensor` and `descriptor.settings` state the camera values. At job assembly the generator writes the `.jsim` (through `dirfm`), the `.platform` (rendered from a library template), the `.ppd` or `.motion`, the `.tasks` and, for `atmosphere.uniform` or `atmosphere.simple`, the `.atm`. Nothing in the job folder is authored by hand.
- **Pass-through.** The engine block names a library directory and a simulation file inside it (`mode: passthrough`), and DIRSIG runs that file as authored. The descriptor is opaque (`opaque: {source: passthrough}`, no `collection`, `sensor` or `settings`). Nothing in the directory can be varied from the spec.

The pass-through form gives a demo a content-addressed reference run; the layered form re-expresses it from stated members. `scripts/compare_layered.py` renders both and compares the bytes (below).

## From DIRSIG input files to engine members

| DIRSIG input | Member | Resolved or generated |
|---|---|---|
| `.scene` (with its `geometry/`, `materials/`, `maps/`) | `engine.scenes[0].ref` and `offset` | resolved: the ref names the `.scene` file and its `content_hash` is the `dirhash/1` digest of the scene's directory; exactly one entry (the loader refuses two); `scene2hdf` compiles a copy in the job |
| `.platform` | `engine.platform.ref`, `library_entry`, `output_prefix`, `split_channels`, `integration_samples`, `channel_response` | generated from the library file as a template (`platform_gen`), with the values `descriptor.sensor` and `descriptor.settings` model; with `as_authored: true`, copied as it is |
| `.ppd` | `engine.motion` with `kind: static`: `position` (`frame: scene`, `xyz`) and `orientation` (`kind: euler`, order, units, `frame: sceneenu`, angles) | generated by dirfm's `PlatformPosition` |
| `.motion` (FlexMotion) | `engine.motion` with `kind: orbit`: a library TLE, `skyfield_sgp4`, the Earth-orientation tables, a window, a waypoint spacing and a LookAt at a scene ENU point with `up: along_track` | generated: the track is propagated outside DIRSIG and written as ECEF waypoints |
| `.tasks` | `engine.tasks.windows` (`start`, `stop`, seconds from `descriptor.collection.epoch`) | generated; `start == stop` is one static sample |
| `.atm` | `engine.atmosphere`: `plugin: new_atmosphere` with a library database ref, or `plugin: basic` with `uniform` or `simple` | resolved (database) or generated (`uniform`, `simple`) |
| weather file | `engine.weather` (`source: library` with a file ref, or `source: install`), or `weather.install_file` inside `uniform` or `simple` | resolved |
| ephemeris | `engine.ephemeris.plugin: spice`, or `fixed_ephemeris` inside `uniform` or `simple` | resolved from the installation, or written into the `.atm` |
| epoch, exposure, frame rate, gain, black level | `descriptor.collection.epoch` and `descriptor.settings[]` (`exposure_time`, `frame_rate`, `gain`, `black_level`) | written into the `.tasks` and the `.platform` |
| `--random_seed` | `engine.run.seed` | passed to `scene2hdf` and `dirsig5` |
| `--threads` | top-level `resources.cpu_threads` | passed to `dirsig5` by the worker |
| files DIRSIG reads from the folder it runs in | `engine.working_folder` | copied into the job's input folder |
| `.sim` or `.jsim` | not stated | written by dirfm |

`motion` kind `waypoints` and `atmosphere` plugin `four_curve` are values the schema lists; they, and `basic` with a file in place of `uniform` or `simple`, are refused by the loader (`manifold.engines.dirsig.run_spec.resolve_run`) with the reason.

## The four members a demo usually needs

A DIRSIG demo is most often a BasicAtmosphere `.atm`, a camera the sensor library does not hold and files read from the demo's own folder. Four members state these. Each is optional, and a spec that does not state one keeps the run id it had before the member existed.

### `atmosphere.uniform`

With `plugin: basic`, `uniform` states a BasicAtmosphere `.atm` that the generator writes into the job (`manifold.engines.dirsig.basic_atmosphere.write_atm`):

- `radiative_transfer.hemisphere_irradiance` and `radiative_transfer.sky_fraction` (DIRSIG's UniformAtm: a spectrally constant irradiance and its diffuse share);
- `weather.install_file`, a weather file of the DIRSIG installation, written as `$DIRSIG_HOME/lib/data/weather/<name>` (the demos use `mls.wth`);
- optionally `fixed_ephemeris` (`units`, `solar_zenith`, `solar_azimuth`).

Rules: such a spec names no library weather file (`engine.weather` absent or `source: install`); with `fixed_ephemeris` it names no `engine.ephemeris`, because DIRSIG replaces the `.atm`'s fixed Sun with a SpiceEphemeris plugin when the job has one; a `uniform` block without `weather` is refused at resolution, because DIRSIG refuses a `.atm` without uniform weather. Turbulence, lunar values, metadata and the classic radiative-transfer form are not written. Tests: `tests/test_uniform_atmosphere.py`.

### `atmosphere.simple`

With `plugin: basic`, `simple` states the same `.atm` with DIRSIG's SimpleAtm in place of UniformAtm: `radiative_transfer.apparent_sky_temperature` (kelvin), and the same `weather.install_file` and optional `fixed_ephemeris` under the same rules. `simple` and `uniform` exclude each other (the schema and the loader refuse both). The job's file is `simple.atm` (`basic_atmosphere.write_simple_atm`). Tests: `tests/test_simple_atmosphere.py`.

### `platform.as_authored`

`as_authored: true` makes the platform ref the job's `.platform` as it is: copied into the job byte for byte and covered by its stamped content hash, so its bytes are in the run id. It is not rendered from the sensor-spec. `descriptor.sensor` and `descriptor.settings` are still loaded and checked but not applied, so the image is in the units the file states (a demo's are usually `watts` per `cm2`, not the generator's electrons per m² of focal plane). `integration_samples` and `channel_response` are refused beside it, with the reason. The library-file check parses the file as a `<platform>` with a focal plane; DIRSIG's dry run reads the rest. Tests: `tests/test_authored_platform.py`.

### `engine.working_folder`

DIRSIG looks for some files in the folder it runs in: the demo's folder in the pass-through form, the job's input folder in the layered form. The loader finds them from the scene, its material file and the platform file (`manifold.engines.dirsig.scene_ref.working_folder_files`) and requires `working_folder` to list exactly those, each as `{name, ref: {name, content_hash}}`: its name in the working folder and its library ref. A missing, mismatched or unneeded entry is refused at resolution, naming the entry; the pass-through form may not state the member. The job copies each file into its input folder. The cases found by measurement are listed in section 3.2 of the CONOPS and Guide: a file the platform names by a relative name (BayerPattern1's `pixels.hdf`), a geometry list beside the `.scene` and outside its `gdbdirectory` (Telecentricity1), and files a material file names by relative names in the keys listed there (Polarization5, BundledMaterials1, MappedTherm1, ChipMaker2, Fireball1, IESSources1). Other material-file keys are not followed. Tests: `tests/test_working_folder.py`.

No committed run spec states `as_authored`, `simple` or `working_folder`: the specs that need them are derived from licensed demo files by `scripts/compare_layered.py` and written only under its work folder. The tests above build their own platform, scene and material files.

## What the layered form cannot express

From section 3.2 of the CONOPS and Guide ("Not in the body") and from [Space_to_space_characterization.md](Space_to_space_characterization.md) ("Axes the SDK cannot express", rounds 29 to 31):

- quaternion orientation, STK report import, a velocity-tracking `up`, `EarthGrid`, jitter, classic radiative transfer and turbulence;
- authored waypoints (`motion` kind `waypoints` is refused), so a stated speed or range for a moving platform: the `orbit` form takes both from the TLE, and the `static` form has no velocity;
- target motion: no member moves a scene object; a mover is scene content (DIRSIG `straight` motion in the scene file);
- more than one scene (the loader takes exactly one `engine.scenes` entry), so an Earth surface behind a generated target; no member adds an Earth model plugin;
- the per-pixel sample count (`--convergence`), the hypersampling multiplier (a template value) and the `::IMPORTANT::` label (scene content);
- `--disable_earth_core` and any other `dirsig5` option except the seed and the thread count; a sub-pixel object therefore needs a surface behind it in the scene;
- a PSF: the sensor-spec has none, and DIRSIG5 applies an aperture-dependent spread of its own unless the platform file states a `<psf>`;
- look angle, phase angle and target radiometry in the descriptor: only `collection.geometry.range` and governed terms have homes; the space-to-space families record the rest under `descriptor.extras`;
- several captures in one task window: DIRSIG's dry run passes such a camera, and `Simulation._check_log` refuses a dry-run log that lists other than one capture per window (C-43);
- the `.atm`'s turbulence, lunar values and metadata, which `uniform` and `simple` do not write.

## The run id

A run id is `manifold.core.identity.run_id(spec, sensor_library)`: the sha256 of the RFC 8785 canonical JSON of the resolved run spec. The resolved run spec is the parsed document with the sensor reference replaced by the referenced sensor-spec's `sensor` block (after its stamped hash is verified), and with `resources` reduced to the slots that can change a result (`cpu_threads`, `gpu`, `assets`, `interpreter`).

Changes the id:

- any member of the parsed document, the descriptor included: a settings value, a settings `provenance` label, `meta.name`, the seed (`tests/test_identity.py`, `test_differences_that_change_the_id`), and equally the description, `fidelity` and `extras`, which no engine reads;
- the bytes of any referenced file, through its stamped `content_hash`: the scene directory's `dirhash/1` digest, the platform's sha256, the database, the weather file, the TLE, each `working_folder` file, and the sensor-spec's `sensor` block;
- a requested `resources.cpu_threads`.

Does not change the id: key order, YAML spelling of the same value, a sensor stated inline instead of by reference (`test_invariances`), the generated file's header comment and composition provenance (not in the parsed document), the directory the recipe is composed from, and `resources.memory_bytes`, `scratch_bytes` and `network`.

Two runs that render the same bytes can therefore have different ids; two runs with one id render from the same stated inputs. Resolution refuses a stamped `content_hash` that does not match its file. Validation lists a `sha256:<hash>` placeholder as unstamped, and submission (`LocalRegistry.submit`, `Workspace.submit_run`) refuses it; `scripts/stamp_hashes.py` stamps the library and layer files.

## Byte-for-byte comparison with the pass-through form

`scripts/compare_layered.py` checks a layered re-expression against the demo run as authored. For each demo, one render at a time, outside the repository:

1. The demo's archive (or a `--source NAME=DIR:SIMULATION` directory) is copied into a private engine-asset library under `--work`.
2. Layers are derived from the demo's own files: the scene and the platform by reference with stamped hashes (the platform `as_authored`), the `.atm` as `uniform` or `simple`, the one-entry `.ppd` as a `static` pose, the epoch and task windows from the `.tasks`, the working-folder files as `engine.working_folder`, and `engine.run.seed` from `--seed` (default 1). The descriptor's sensor is a library stand-in, checked but not applied.
3. Three renders through `Workspace.local`: the layered recipe, the pass-through form at the same seed, and the pass-through form without a seed.
4. Every image both forms wrote is compared: shape, per-band means, maximum absolute difference, the fraction of differing pixels, and each file's sha256. The table's last column is "yes" only when the two digests are equal.
5. When the layered image differs from the same-seed pass-through one, the layered job's input folder is rendered once more by `dirsig5` directly with the demo's own motion file, then with only the demo's Euler angles, and the digests are compared again.
6. At DIRSIG's default thread count (no `--threads`), when the layered image differs, the same-seed pass-through spec is rendered once more in a second run store and compared with the first; if the two differ, the report prints a noise-floor note: a digest difference is then no evidence of an input difference.

`--threads N` requests N threads for every render: the layered engine profile and the pass-through specs carry `resources: {cpu_threads: N}` (their run ids differ from the default's), and step 5's direct renders get `--threads=N`. Without it no count is requested.

The script lists the input differences it knows (`KNOWN`): the simulation file is dirfm's; the `.ppd` and `.tasks` are regenerated (positions to 3 decimals, Euler angles to 6, the epoch in UTC); dirfm writes an explicit zero scene offset; the `.atm` carries only the derived values; dirfm compiles the scene with `--threads` and the seed, the pass-through runner with neither; the layered job runs with the user's `HOME`, the pass-through run with a per-run `HOME`; the two forms run in different working folders. `docs/DIRSIG_layered_comparison.md` records the results: every demo compared to the end renders byte-identical to its same-seed pass-through render, image and truth, or differs only by one or more of these listed differences, each shown by restoring it; the demos stopped before a comparison are listed there with the reason.

A digest comparison is exact only where the reference repeats. At DIRSIG's default thread count some scenes do not: a repeat of either form of the transferred foxbat scene changes every digest (0.09 to 0.10 % of pixels, `docs/DIRSIG_transfer_scenes.md`), and one thread made the radiance of every repeat in the determinism probe bit-identical (`docs/DIRSIG_determinism.md`).

## Worked specs

Three committed run specs, each admitted by the engine-free checks (`manifold.core.admission.validate_spec`).

### 1. A generated scene under a uniform atmosphere

`manifold_run_specs/s2s/s2s-hyperresolved-r25km-v0mps-e5ms-l0-z0-d0.yaml`, written by `scripts/s2s_scenarios.py`: a 20 m Lambertian plate in a generated library scene, seen from 25 km at nadir. Its atmosphere is `uniform` with a fixed Sun, so it names no weather file and no ephemeris plugin:

<!-- block: spec manifold_run_specs/s2s/s2s-hyperresolved-r25km-v0mps-e5ms-l0-z0-d0.yaml engine.atmosphere -->
```yaml
plugin: basic
uniform:
  radiative_transfer:
    hemisphere_irradiance: 0.1
    sky_fraction: 0
  weather:
    install_file: mls.wth
  fixed_ephemeris:
    units: degrees
    solar_zenith: 0.0
    solar_azimuth: 0
```

Its pose is `static`: 25 km above the plate, turned by pi about z:

<!-- block: spec manifold_run_specs/s2s/s2s-hyperresolved-r25km-v0mps-e5ms-l0-z0-d0.yaml engine.motion -->
```yaml
kind: static
position:
  frame: scene
  xyz:
  - 0.0
  - 0.0
  - 25000.0
orientation:
  kind: euler
  euler:
    order: xyz
    units: radians
    frame: sceneenu
    angles:
    - 0.0
    - 0.0
    - 3.141592654
```

It requests one thread (one thread repeats bit for bit), so the request is in its id:

<!-- block: spec manifold_run_specs/s2s/s2s-hyperresolved-r25km-v0mps-e5ms-l0-z0-d0.yaml resources -->
```yaml
cpu_threads: 1
```

Its run id is `a52a29f90622ab078ac14a7c4b2dbd4fbb0f462607c3113067d2cf70560b6155`, as `manifold_run_specs/s2s/index.json` records. The family's specs and index are regenerated and compared by:

<!-- block: command -->
```bash
python scripts/s2s_scenarios.py --check
```
