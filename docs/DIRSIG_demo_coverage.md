# DIRSIG demo coverage

Which of DIRSIG's 151 shipped demos the SDK could regenerate today, and what each still needs. Generated by `python scripts/survey_demos.py --out docs/DIRSIG_demo_coverage.md` from the demo archives in the DIRSIG installation (`external/dirsig/demos/zips`), read in place; regenerate it after a loader feature lands. It is derived from file names, plugin and element names, counts and sizes only, and contains no demo file contents.

A verdict compares a demo's simulation file, platform, motion and atmosphere with what the SDK's engine body and loader cover (the run-spec contract's engine block and `run_spec.resolve_run`): `ready` needs nothing new (one scene, `NewAtmosphere` with a `ThermWeather` file, SPICE ephemeris, static or orbit motion, one imaging instrument); `near` needs exactly one missing feature; `far` needs two or more, or has a non-imaging sensor; `unparsed` means the layout was not understood, with the reason. A value that cannot be read is `unknown`. A legacy `.sim` carries its atmosphere and uniform weather in one `.atm` file, counted as one feature, and its ephemeris is implicit. Platform features are recognized by element name (lens distortion, point spread function, field selectors and so on); a behaviour with no distinct element, such as a rolling shutter, is not seen, so a `near` verdict is an upper bound on readiness. Scene size is the `.scene` file and the archive members it references.

## First demo: what it took

`PointCollectors2`, the first recommendation, placed in the library and validated at level `none` (`Workspace.local().validate("pointcollectors2_demo")`). It composes and passes the schema check; it does not validate yet. Findings about the SDK, in the order the loader meets them:

1. Placement works: three assets (the scene directory with `demo.scene`, `demo.glist` and `demo.mat`, 1987 bytes; `demo.platform`, 3940 bytes; `uniform.atm`, 1155 bytes) are described in `manifold_config_repo/assets.json`, with digests computed from the archive members without extracting, and `scripts/bootstrap.py assets` placed them under the gitignored `manifold_config_repo/demos/PointCollectors2/` and verified them; `scripts/stamp_hashes.py` stamped the same digests into the engine profile.
2. The scene fits the library layout as `demos/PointCollectors2/scenes/demo/demo.scene` with the files it references kept at their relative paths; it resolves and its `dirhash/1` digest verifies.
3. The loader refuses `engine.atmosphere.plugin: basic` ("this loader handles only 'new_atmosphere'"): a BasicAtmosphere `.atm` file needs a loader feature and a schema form for `basic` (today the schema leaves its members open, so the file reference is accepted unchecked).
4. That refusal carries no `RunSpecError.pointer`, so its problem names no layer or field; the loader's plugin refusals should point at the member they refuse.
5. With the atmosphere replaced in memory, the loader refuses `engine.weather.source: install`: the demo's weather is the uniform weather inside its `.atm` file, and the SDK accepts only a library ThermWeather file, so uniform weather needs a form of its own.
6. With the weather replaced too, the demo's `.platform` is not a template the platform generator can fill ("template must have exactly one .//temporalintegration, found 0"): the generator expects the layout of the repository's AUROR template, so a demo platform needs either a template-compatible variant or a generator that accepts its capture method as written.
7. The demo's camera could be written as a `sensor-spec/1` document only by copying values from its licensed platform file, and its epoch, pose and viewing geometry only by copying from its tasks and motion files; none of that may be committed, so the layers use a library stand-in sensor and stand-in collection and pose. Regenerating a demo needs those values derived at bootstrap time into a gitignored layer overlay, or a licence that allows committing them.
8. The demo's motion and tasks files are not library assets: the SDK generates motion and tasks from the run spec, so their values belong in the engine profile and scenario (point 7 applies).
9. The survey chose `framing.jsim` as the simulation file because the demo has no `demo.jsim`; the choice of variant decides which plugins and files a regeneration must cover.
