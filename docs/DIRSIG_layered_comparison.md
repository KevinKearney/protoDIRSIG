# DIRSIG demos: layered form against pass-through

Comparisons of DIRSIG demos expressed in the layered form (CONOPS section 3.2: `engine.atmosphere.uniform`, C-39, `engine.atmosphere.simple`, C-41, `engine.platform.as_authored`, C-40, and `engine.working_folder`, C-42) with the same demo run as authored through the pass-through form. Numbers and digests only; no output byte and no demo value is in this repository.

**How.** `python scripts/compare_layered.py DensityMap1 MaterialMap1 PointCollectors2 --work <outside the repository>` (2026-10-12, DIRSIG 2026.38 (a020954), dirfm 93195ce, 36 s for all renders). Per demo the script extracts the demo's archive into a private library under `--work`, derives the layers from the demo's own files (the scene and platform by reference and hash, the `.atm` read with `basic_atmosphere.read_atm`, the one-entry `.ppd` as a static pose, the `.tasks` as epoch and windows), renders the layered recipe, the pass-through form at the same seed and the pass-through form without a seed, one at a time at the demo's native size, and compares every image both forms wrote. The derived layers hold the demo's licensed values, so they are written only under `--work` and are not committed as recipes (section 5.1); the script is the recipe's source. Seed: 1 for the layered run and the same-seed pass-through run.

**Round two (2026-10-12, same DIRSIG and dirfm).** `python scripts/compare_layered.py ColorFilterArray1 BayerPattern1 LensDistortion1 ReflectanceMap1 Telecentricity1 PolyFill1 PrimitiveObjects1 Indoors1 --work <outside the repository> --timeout 1200` (160 s for all renders): the first eight `ready` demos of the sweep report's candidate list with a deterministic reference, in its order of reference cost (`docs/DIRSIG_demo_sweep.md`, "Layered-comparison candidates"). The script was extended for them: a `.scene` origin written as `<geodeticlocation>`, a `.jsim` that names `SpiceEphemeris` without inputs (the plugin the layered job adds itself), the pass-through renders kept after a failed layered render, and a second attribution render with the demo's Euler angles alone. BayerPattern1 and Telecentricity1 were rendered again by the extended script (`--work` elsewhere) for their pass-through digests; PolyFill1, PrimitiveObjects1 and Indoors1 again for the angles-only attribution, reproducing every run id and image digest of the first run.

**Round three (2026-10-12, same DIRSIG and dirfm).** With `engine.working_folder` built (the files DIRSIG looks for in the working folder, copied into the job's input folder), `python scripts/compare_layered.py BayerPattern1 Telecentricity1 Polarization5 --work <outside the repository> --timeout 1200` (8 min 10 s, 460 s of it Polarization5's two pass-through renders): the script states the files `scene_ref.working_folder_files` finds as `engine.working_folder` (BayerPattern1 `pixels.hdf`, named by `bayer_hdf.platform`; Telecentricity1 `demo.glist`, named by `demo.scene`, and `Sphere.obj`, named by `demo.glist`; Polarization5 `pixels.dat`, named by `pi.platform`). The two layered run ids differ from round two's, because the specs now state `working_folder`; the pass-through run ids and digests are round two's.

The `nan` band of DensityMap1's truth image is NaN in some pixels of both forms; pixels NaN in both are not counted as differing. "Pixels differing" counts a pixel when any band differs. BayerPattern1 and Telecentricity1 have rows from round three only (their round-two layered runs failed in DIRSIG's dry run); Polarization5 has none (its layered run failed in the dry run, below). Indoors1's and Telecentricity1's truth images hold NaN and infinite values in both forms, so their means are NaN or infinite and a maximum difference can be infinite.

**MaterialMap1.** The layered render is byte-identical to the pass-through render at the same seed, image and truth. Only the image headers differ: the acquisition time is written in UTC (`2000-08-01T18:00:00.0000+00:00`) by the layered form and with the demo's offset (`13:00:00.0000-05:00`) by the pass-through form, the same instant; and the geolocation corners in the last digits.

**DensityMap1.** The layered render differs from the same-seed pass-through render in almost every pixel, by Monte Carlo noise around equal means (0.045067 against 0.0450775). Attribution (the script's step 5, a diagnostic outside the recipe): the layered job's own input folder rendered again with the demo's `.ppd` in place of the generated one gives the pass-through digests exactly (`demo.img` db5d5511..., `demo_truth.img` 23429245...). Two further diagnostic renders narrowed it to the Euler angles: dirfm's `PlatformPosition` writes them to six decimals (1.047198 for the demo's 1.04719755, 5.759587 for 5.75958653), and restoring the two values alone gives the pass-through digests, while writing the location's `frame` attribute in place of dirfm's `type` changes nothing. The tasks file, the jsim's plugin order, the scene compile's seed and thread count, and the cache (user HOME against a per-run HOME) made no difference here. MaterialMap1's angles are 0, which six decimals hold exactly.

**PointCollectors2.** First run (2026-10-12, before the fix): the layered run failed in DIRSIG's dry run, `demo.mat` "is not a file" in the job's scene copy. The demo's `.scene` names `demo.glist` and `$SCENE_DIR/demo.mat`, files beside it, and the scene reference (`scene_ref.reference_scene`) linked only the `geometry/`, `materials/` and `maps/` folders beside a `.scene` (BACKLOG "Tagged demos: loader gaps", item 11). Since then the job copies the files a `.scene` names beside it (`scene_ref.scene_named_paths`; CONOPS section 3.2, `scenes[]`), and `python scripts/compare_layered.py PointCollectors2 --work <outside the repository>` (2026-10-12, same DIRSIG and dirfm, 19 s) gives a layered render byte-identical to the same-seed pass-through render, image and truth. The truth image's per-band means are NaN because about half its pixels are NaN in every band and its last band is NaN throughout; pixels NaN in both forms are not counted as differing. Its `.atm` fixes the Sun and its `framing.jsim` names no ephemeris plugin, so neither form adds one. The layered run id is the one the first run had: the fix changes the job folder, not the run spec.

**ColorFilterArray1, LensDistortion1, ReflectanceMap1: byte-identical.** Each layered render is byte-identical to the same-seed pass-through render, image and truth (digests below). Product files: the truth headers are identical; the image headers differ in one line, the acquisition time, written in UTC by the layered form and with the demo's offset by the pass-through form (as for MaterialMap1). The layered run also writes `run_info.json` and `log_info.json` (the SDK's run record), which the pass-through runner does not. LensDistortion1's layered image is also byte-identical to the no-seed reference (its truth image is not). ColorFilterArray1 and LensDistortion1 carry their camera feature (a colour filter array, lens distortion) in the platform used as authored.

**PolyFill1, PrimitiveObjects1, Indoors1: differ by a listed input difference, the pose's Euler angles.** Each layered render differs from the same-seed pass-through render by Monte Carlo noise around nearly equal means. Diff of the job inputs: the generated `.ppd` holds the demo's position exactly and its Euler angles to six decimals (PolyFill1 1.047198 and 5.759587 for 1.04719755 and 5.75958653, the values DensityMap1 has; PrimitiveObjects1 0.811726 and 5.961435 for 0.81172612 and 5.96143475; Indoors1 1.570796 for 1.57079633). Controlled variation (the script's step 5): the layered job's own input folder rendered again with the demo's `.ppd`, and again with the generated `.ppd` whose three angles alone are the demo's text, gives the same-seed pass-through digests exactly, image and truth, for all three demos. Product files: the truth headers are identical; the image headers differ in the acquisition time (PolyFill1, PrimitiveObjects1) and in the geolocation corners in the last digits (all three). A control render of PolyFill1's layered job assembled by the SDK's `Simulation` without the variation reproduced the layered digests.

## Known input differences

Listed for every comparison, whether or not it changed a number:

- simulation file: the layered job's jsim is written by dirfm (BasicPlatform, BasicAtmosphere, and SpiceEphemeris unless the `.atm` fixes the Sun), not the demo's own `.sim` or `.jsim`; MaterialMap1's `.atm` fixes no Sun, so its layered job names SpiceEphemeris where the `.sim` relies on DIRSIG's implicit ephemeris;
- motion and tasks: regenerated by dirfm from the derived values (the `.ppd` with positions to three and Euler angles to six decimals, the `.tasks` with the epoch in UTC);
- `.atm`: written from the derived uniform or simple values; the demo's `<metadata>`, `<turbulence>` and lunar values are not carried;
- seed: the layered run states 1; the sweep's references state none (DIRSIG's default seed), so the same-seed pass-through run is the like-for-like reference;
- scene compile: dirfm runs `scene2hdf` with `--threads <cpu count>` and the seed; the pass-through runner runs it with neither;
- cache: the layered job runs with the user's HOME; the pass-through run with a per-run HOME;
- working folder: DIRSIG runs a pass-through job in the demo's folder and a layered job in the job's input folder, with the scene copy in a subfolder of it and the platform at its library path; a file DIRSIG looks for in the working folder is found by the first and, unless `engine.working_folder` places it there (since round three: files a platform names, geometry lists beside the `.scene` outside its `gdbdirectory` and what they name), not by the second (BayerPattern1 and Telecentricity1 in round two; files a material file names, Polarization5);
- descriptor: the layered run's sensor-spec is a library stand-in, checked but not applied (the platform is used as authored), and its collection states the scene origin and the pose's height.
